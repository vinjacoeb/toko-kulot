(a) Validasi di klien memakai aturan + pesan yang sama dengan server.
    Checkout.jsx baris 43–78 (pola di baris 12–14):

function validate(values) {
    const errors = {};
    const teks = (nilai) => String(nilai ?? '').trim();

    const nama = teks(values.customer_name);
    if (nama === '') errors.customer_name = 'Nama penerima wajib diisi.';
    else if (nama.length < 3) errors.customer_name = 'Nama penerima minimal 3 karakter.';
    else if (nama.length > 100) errors.customer_name = 'Nama penerima maksimal 100 karakter.';

    const telepon = teks(values.customer_phone);
    if (telepon === '') errors.customer_phone = 'Nomor WhatsApp wajib diisi.';
    else if (!PHONE_PATTERN.test(telepon)) errors.customer_phone = 'Nomor WhatsApp tidak valid.';
    ... (email, alamat, kota, kode pos, catatan; semuanya memakai teks()/trim yang sama)

    const kodePos = teks(values.customer_postal_code);
    if (kodePos === '') errors.customer_postal_code = 'Kode pos wajib diisi.';
    else if (!POSTAL_PATTERN.test(kodePos)) errors.customer_postal_code = 'Kode pos harus 5 angka.';

    if (teks(values.note).length > 500) errors.note = 'Catatan maksimal 500 karakter.';

    return errors;
}

    Padanan aturan server (app/Http/Requests/CheckoutRequest.php baris 24–32) satu per satu:
      customer_name        required|string|min:3|max:100   -> wajib / min 3 / maks 100
      customer_phone       required|regex ^(\+62|62|0)8[0-9]{7,12}$ -> PHONE_PATTERN identik
      customer_email       required|email|max:150          -> diisi / pola / maks 150
      customer_address     required|string|min:10|max:500   -> diisi / min 10 / maks 500
      customer_city        required|string|min:3|max:100    -> diisi / min 3 / maks 100
      customer_postal_code required|string|digits:5         -> diisi / 5 angka
      note                 nullable|string|max:500          -> hanya maks 500 (opsional)

    Klien tidak pernah lebih ketat dari server: pola email dilonggarkan ke
    /^[^\s@]+@[^\s@]+\.[^\s@]+$/ (tanpa syarat TLD >= 2 huruf) supaya nilai yang diterima
    server (filter_var) tidak diblokir di klien.

====================================================================
4. BELUM DIUJI — BUTUH BROWSER (langkah aman untuk pemilik)
====================================================================
Kondisi: server pengembangan sudah berjalan di http://127.0.0.1:8000 dengan keranjang berisi
minimal satu produk. Tidak ada perintah server/migrasi yang dijalankan dari sisi frontend.

  Skenario a (validasi klien)
    1. Buka /checkout, langsung tekan tombol "Buat Pesanan" tanpa mengisi apa pun.
    2. Harap: tidak ada permintaan jaringan baru (DevTools > Network), muncul notice merah
       "Ada 6 kolom yang perlu diperbaiki" di atas formulir DAN tepat di atas tombol,
       dengan "Kolom pertama Nama Penerima: Nama penerima wajib diisi."
    3. Isi nama 2 huruf -> setelah kirim, pesan "Nama penerima minimal 3 karakter."
  Skenario b (tombol Perbaiki kolom)
    4. Klik "Perbaiki kolom" -> layar menggulir ke kolom pertama yang salah DAN kursor masuk
       ke kolom itu (fokus terlihat). Ulangi dari notice yang ada di dekat tombol "Buat Pesanan".
  Skenario c (galat dari server)
    5. Isi semua kolom dengan nilai sah, lalu kirim. Jika server menolak (mis. email ditolak
       validator server), halaman menggulir sendiri ke kolom pertama yang bermasalah tanpa
       memindahkan fokus, dan notice muncul di dua tempat.
  Skenario d (anti kirim ganda)
    6. Klik "Buat Pesanan" dua kali cepat saat koneksi lambat (throttling Network ke Slow 3G):
       tombol harus nonaktif/berputar dan hanya ada SATU permintaan POST /checkout.
  Tampilan & aksesibilitas (belum diuji):
    7. Lebar 360 / 768 / 1024 / 1280 px: formulir satu kolom di 360, dua kolom + ringkasan
       sticky di >=1024; notice tidak meluber.
    8. Keyboard saja: Tab melewati kolom menurut urutan formulir, tombol "Perbaiki kolom"
       dapat dijangkau dan diaktifkan Enter/Space, indikator fokus terlihat.
    9. Zoom 200%: tidak ada teks/notice terpotong. Aktifkan "reduce motion" di OS ->
       gulir menjadi tanpa animasi (tidak meluncur).

====================================================================
5. ASUMSI
====================================================================
1. Kontrak props (§7.6/§7.8) hanya memuat daftar field + aturan server; tidak ada tabel aturan
   validasi klien tersendiri. Karena itu pesan dan aturan klien disalin dari
   app/Http/Requests/CheckoutRequest.php (satu-satunya sumber aturan yang ada di repo) dan
   server tetap penentu akhir. Tidak ada kontrak baru yang dibuat.
2. `note` tidak dapat melewati 500 karakter lewat UI (atribut maxLength pada Textarea), tetapi
   validate() tetap memeriksanya agar pesan server tercermin lengkap.
3. Pola email klien sengaja dilonggarkan (tanpa syarat TLD >= 2 huruf) supaya tidak lebih ketat
   dari aturan `email` server.
4. Tidak ada paket atau pustaka uji baru yang dipasang; harness memakai React + stub yang sudah
   ada di tmp/ dari kartu sebelumnya.
